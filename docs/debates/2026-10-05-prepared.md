# Design debates prepared for Mon 05/10 (not started)

Prepared Sun 04/10 by the lead. Launch only after Mauro says go. Each debate runs as an agent team (max 4 active), and every teammate touches no code: the output is a decision memo, nothing else.

## Format (both debates)

1. **Propose (30 min agent time).** Each participant writes one proposal, max 1 page, in `docs/debates/<debate>/<teammate>.md`: design, what it costs in agent-hours and Mauro-hours, what it breaks or defers.
2. **Refute (one round).** Each participant reads the other proposals and appends objections to them under `## Objections from <teammate>`. An objection must name a concrete failure (an attack, a failed test, a missed deadline, a rule in `CLAUDE.md` or an AD it violates). Style comments do not count.
3. **Answer (one round).** Each author answers the objections against their own proposal: accept and amend, or rebut with evidence.
4. **Lead brings Mauro:** the proposal that survived, the objections that still stand, the cost of each in hours, and the decision Mauro has to make. Max 1 page, in `docs/debates/<debate>/summary.md`. Mauro decides; the decision goes to `docs/03-architecture-decisions.md` as a new AD.

qa never defends its own proposal in the gate later; whichever design wins, a different qa pass reviews the implementation.

- How the client builds these txs for Phantom via Solana Pay transaction requests (sol-client), and what the custodial fallback looks like with the same `PaymentIntent`.

## Debate B — Reusable session (replace the replayable signed blob)

**Participants:** fullstack (fullstack-engineer), sol-client (solana-client-engineer), qa (qa-security-reviewer).

**Question:** how a session survives across requests and devices from F2 on, so that a resent old session can never pay twice and the agency panel can read the same state.

**Inputs:** `docs/reviews/phase-0.md` issue 1 (signed session is replayable: resending a pre-deposit blob to `/api/pay` pays the deposit again), issue 5 (rate limit per instance), AD-11b (Neon + Drizzle), R0-4 and R2-1 (keep the signed-session path as demo fallback), AD-10b (no embedded wallet; Phantom by QR), `lib/db/session.ts`, `app/api/pay/route.ts`.

**Candidate designs to seed the debate:**
- fullstack: server-side session in Neon keyed by an opaque cookie; the client holds only the id; payments recorded in a table with a unique `(lease_id, kind, month_index)` constraint.
- sol-client: keep the client-held blob, but before paying check on chain (memo lookup by `leaseId` and kind/month, or the PaymentRecord PDA in program mode) and refuse if it already exists.
- qa: the attack list both must survive: replayed blob, two tabs paying at once, two serverless instances, cold start mid-payment, a confirmed tx whose response was lost, RPC lag on the memo lookup.

**Must also answer:** "reusable" across what (tabs, devices, tenant returning a month later, agency viewing it); idempotency key for `/api/pay`; what happens in REPLAY mode; migration from the current blob without breaking the recorded demo; cost in agent-hours and Mauro-hours against the 2.5 h of slack in PLAN §1.
